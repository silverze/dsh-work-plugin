# 屏幕与飞书上下文感知

有两条读取通道，优先用第一条：

| 通道 | 工具 | 成本 | 适用 |
| --- | --- | --- | --- |
| 本机 OCR（默认） | `work_feishu_screen`、`work_screen_text` | ~1 秒，几百 token | 飞书、微信、企业微信等 Chromium 客户端；任何应用窗口 |
| 辅助功能树（兜底） | `cua` → `getState` + `work_feishu_focus` | 深读可达数万 token | OCR 不可用，或需要按钮/输入框等控件而非文本时 |

飞书的网页内容在辅助功能树里几乎是空的（只看到 `AXWebArea "messenger"` 和一堆空 `AXGroup`），要读到会话标题得下钻 26 层以上，代价极高，所以**不要**一上来就 `cua` 深读。

## 标准流程

1. `work_frontmost_app` — 零权限、毫秒级。若不是飞书/企业微信/浏览器，先判断用户是否真的在飞书上，别盲读屏幕。
2. `work_feishu_screen` — 自动发现飞书进程（含公司定制版，如"小米办公Pro"），截取会话窗口做 OCR，直接返回：
   - `chatName`：当前聚焦的会话名（优先取输入框的「发送给 X」，其次取标题栏）
   - `chatKind`：`group` / `direct` / `unknown`（没有正证据时不要猜）
   - `messages`：该会话当前可见的消息文本，按屏幕顺序（旧→新）
   - `otherChats`：左栏里同时打开的其他会话名，用来确认"聚焦的是这一个而不是那一个"
3. 需要别的应用（企业微信、微信、浏览器、Excel）时用 `work_screen_text`，参数是 `pid`（从 `cua` → `listApps` 取），返回该窗口可见文本，自上而下。
4. 只在 OCR 失败（返回 `detected: false` 或 `error`）时，才退回 `cua` → `getState` 取辅助功能树，把文本交给 `work_feishu_focus` 解析。

回答时明说判断依据，例如"当前会话是「示例项目开发测试群」（依据：输入框显示「发送给 …」）"，让用户能一眼纠正。

## 用户已经引用过时，不要再读屏

开启工作模式的会话，输入框下方有一个「飞书当前会话」chip。用户点一下就会把当前飞书会话作为 blockquote 插入草稿，首行形如 `> 飞书群聊「…」· 10:32 屏幕可见 N 行（OCR，最旧在上）：`。

看到这种引用块时：直接用它，**不要**再调 `work_feishu_screen` 重复读屏；用户已经选好了会话，也不需要再问"你说的是哪个群"。只有引用块内容不足以回答（例如需要更早的消息）时，才读屏或请用户补充。

## 边界

- **只读**。发送消息、点按钮、切会话都要用户明确要求，并先把待发内容念给用户确认。
- 只读回答问题所需的范围：用户问 A 群就只看 A 群，不翻别的会话或私聊。
- 屏幕上的内容默认只用于本次回答，**不要**未经确认写进交付文档、上传飞书或转发。
- 屏幕里可能混着无关敏感信息（密码、工单号、别人私聊）：引用时做最小化摘录。

## 失败时怎么说

- `No Feishu conversation recognized` / `No window found for pid`：
  1. 让用户确认飞书窗口没有被最小化、在当前桌面上可见；
  2. 打开「系统设置 → 隐私与安全性 → 屏幕录制」，确认 **DeepSeek Harness**（截图由宿主进程发起）已勾选；首次调用 OCR 时系统可能弹一次授权窗，需要点"允许"；
  3. 首次调用会用 `swiftc -O` 编译 OCR 辅助程序（约 20–30 秒，之后复用缓存），若报缺 `swiftc`，装 Xcode Command Line Tools：`xcode-select --install`。
- 退回辅助功能树的路径要求「系统设置 → 隐私与安全性 → 辅助功能」里勾选 **DSH Computer Use.app**；`osascript` 报 `不允许辅助访问 (-1728)` 就是这条没开。
- 两条都不可用时，不要反复重试：请用户把关键几句复制过来，先把活干完。
